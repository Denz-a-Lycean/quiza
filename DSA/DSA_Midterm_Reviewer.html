Module 01 — Search Algorithms
Finding Data Efficiently
Two fundamental approaches to locating a value in a dataset. Choose based on your data's condition.
🧠 Golden Rule
"Linear for Unsorted, Binary for Sorted"
Binary search is faster but requires sorted data. If your list changes frequently or is small, just use linear. Binary wins only when you search many times on static/sorted data.
🔎
Linear Search
Also called Sequential Search. Brute force — check every element one by one until found or list ends.

✓ No prerequisite  O(n) worst

Use when: Small list, unsorted data, data changes often.
⚡
Binary Search
Divide & Conquer. Checks the middle, discards half. Repeats on the relevant half.

✗ Must be sorted  O(log n)

Use when: Large list, sorted data, searched many times.

⚠️ The Hidden Cost of Binary Search
If your data is unsorted, you must sort it first. Sorting costs O(n log n). Then binary search adds O(log n). Total: O(n log n). If you search only ONCE on unsorted data, Linear Search (O(n)) is actually FASTER!
Linear Search — How It Works
// Linear Search in C-style pseudocode for(i=0; i<n; i++) { if(list[i] == target) { // Found! Return index i break; } // else: move to next element }
Binary Search — How It Works
// Binary Search — data MUST be sorted low = 0; high = n-1; while(low <= high) { mid = (low + high) / 2; // Find middle if(arr[mid] == target) // Found! return mid; else if(arr[mid] < target) low = mid + 1; // Go right else high = mid - 1; // Go left }
Types of Search Keys
🔑 Primary Key
Unique identifier. Only one record matches. (e.g., Student ID, Roll No.)
🏠 Secondary Key
Non-unique. Multiple records may share it. (e.g., Address, Last Name)
📦 Internal Key
Embedded within the record itself. The key is part of the data structure.
🔗 External Key
An external entity used to refer to records. (like a foreign key in databases)
Module 02 — Sorting Algorithms
Arranging Data in Order
Sorting enables faster searching and better data organization. Know when to use each algorithm.
🧠 Mnemonic — Simple Sorts
"BSI" = Bubble, Selection, Insertion → All O(n²)
Simple sorts are all O(n²). They're slow but easy to understand. Good for small data or nearly sorted data (Insertion Sort especially).

Each Algorithm Explained
Repeatedly compares adjacent elements and swaps if they're in the wrong order. Larger elements "bubble up" to the end.

Steps:
  1. Compare arr[0] and arr[1]. If arr[0] > arr[1], swap.
  2. Move to arr[1] and arr[2]. Repeat.
  3. After one full pass, largest is at the end.
  4. Repeat for remaining elements.
Optimization: If no swaps in a pass, the list is sorted → Best case O(n).
Finds the minimum element in the unsorted portion and places it at the beginning. Always O(n²) — no optimization possible.

  1. Find the minimum element in the entire array.
  2. Swap it with the first element.
  3. Consider the rest of the array (excluding first).
  4. Repeat until sorted.
Builds the sorted array one item at a time. Takes one element and inserts it into its correct position among already-sorted elements.

  1. Start from the second element (index 1).
  2. Compare with elements before it.
  3. Shift larger elements one position right.
  4. Insert the element in its correct position.
  5. Move to the next element.
Best for nearly sorted data. Very efficient for small datasets.
Divide and Conquer. Split array in half recursively, then merge back in sorted order.

  1. Divide: Split the array into two halves.
  2. Conquer: Recursively sort each half.
  3. Glue: Merge the two sorted halves back together.
Tradeoff: Guaranteed O(n log n) always, but needs O(n) extra memory (out-of-place sorting).
Choose a pivot. Partition: elements ≤ pivot go left, elements > pivot go right. Recursively sort partitions.

  1. Choose a pivot element (usually last or middle).
  2. Partition: put smaller elements left, larger elements right.
  3. The pivot is now in its final position.
  4. Recursively apply to left and right partitions.
Worst Case: If pivot is always the smallest/largest (already sorted list with leftmost pivot) → O(n²). Solution: use random pivot or median-of-three.
Uses a max-heap data structure. The heap is stored as an array (no pointers needed!). Height is always O(log n).

  1. Build Max Heap: Rearrange array into a max-heap.
  2. Extract Max: Swap root (max) with last element A[n].
  3. Restore: Run Max_Heapify on the new root. Shrink heap by 1.
  4. Repeat steps 2-3 until heap has one element.
Key Advantage: O(1) extra space (in-place). Worst case is guaranteed O(n log n).
🧠 When to choose which sort?
Q = Quick (speed), M = Merge (guaranteed), H = Heap (memory-lean)
Quick Sort → Default choice. Fastest empirically, cache-friendly. Watch for sorted-input pitfall.
Merge Sort → When stability or guaranteed O(n log n) is required and extra memory is OK.
Heap Sort → When O(1) space is critical. Slightly slower than Quick in practice.
Insertion Sort → When list is small or nearly sorted.
Bubble/Selection → Educational purposes only. Never in production.
Module 03 — Tree Data Structures
Hierarchical Data Organization
Trees organize data for fast searching, insertion, and deletion. Understanding the evolution from Binary Tree → BST → Self-Balancing → B-Trees is key.
🧠 Tree Evolution — Remember This Chain
Binary Tree → BST → AVL/Red-Black → B-Tree → B+ Tree
Each step solves a problem with the previous. BT has no order → BST adds order → BST can degenerate → AVL/RB stay balanced → Binary trees are too tall for disk → B-Trees are wide and short → B-Trees can't do range queries fast → B+ Trees add leaf links.

Tree Traversals — The 3 Orders
1
Pre-order (NLR)
Node → Left → Right

Visit root FIRST, then go left, then go right.

Use for: Copying/reconstructing the tree
2
In-order (LNR)
Left → Node → Right

Visit left subtree, then root, then right.

Use for: Getting a sorted sequence from BST
3
Post-order (LRN)
Left → Right → Node

Visit both children before the root.

Use for: Deleting tree or evaluating expressions
🧠 Traversal Trick
Pre = Root FIRST | In = Root MIDDLE | Post = Root LAST
The "pre/in/post" refers to WHEN you visit the root relative to children. Pre-order: root before children. In-order: root between children (gives sorted output for BST). Post-order: root after children.
Tree Types — Evolution
Each node has at most 2 children (left and right). NO ordering rule. Nodes are added wherever there's space.

The Flaw: Because there's no order, searching requires scanning potentially ALL nodes → O(n) worst case. It's essentially a linked list with two pointers.
Use for: Org charts, parsers, arbitrary hierarchical mapping where order doesn't matter.
The Golden Rule: Left child < Parent < Right child (for every node!)

This means at each node, you can discard half the tree — cutting search time to O(log n).

BST Search Steps:
  1. Start at root.
  2. If target = current → FOUND.
  3. If target < current → go LEFT.
  4. If target > current → go RIGHT.
  5. Repeat until found or NULL.
Time: O(h) where h = height of tree.
BST Deletion — The 3 Cases:
Case 1 — Leaf node: Just delete it. Done.
Case 2 — One child: Replace the deleted node with its child (subtree shifts up).
Case 3 — Two children: Replace with the in-order successor (leftmost node of right subtree — the smallest in the right side). This is "The Successor Rule."
The Degeneration Flaw: If you insert sorted data (1,2,3,4,5...), BST becomes a linked list! Height = n, search = O(n). This kills the advantage entirely.
AVL trees automatically re-balance after every insertion/deletion. Balance Factor = Height(left) − Height(right) must be -1, 0, or +1 for every node.

How it balances: Rotations — LEFT-ROTATE(T, x) or RIGHT-ROTATE(T, y)
Rotations are O(1) — they just change a constant number of pointers.
After rotation, BST ordering is perfectly preserved.
Rotation preserves these relationships:
  • x is less than y
  • alpha < x < y
  • x < beta < y
  • gamma > x and y
Result: Always O(log n) for search, insert, delete. More frequent rotations than Red-Black.
Uses color rules instead of strict height balancing. Less rotations than AVL = faster for frequent insertions/deletions.

The 4 Rules:
  1. Every node is either RED or BLACK.
  2. The root is always BLACK.
  3. No two consecutive RED nodes (red node's children must be black).
  4. Every path from root to a NULL leaf has the same number of BLACK nodes.
Guarantee: No path is more than twice as long as any other. This ensures height ≤ 2 log(n+1) → operations are O(log n).
AVL vs Red-Black: AVL is more strictly balanced (better for lookup-heavy). Red-Black allows slight imbalance but fewer rotations (better for insert/delete-heavy). Real-world use: Java's TreeMap, Linux kernel use Red-Black.
The Problem B-Trees Solve: Memory access = nanoseconds. Disk access = milliseconds. A tall binary tree with millions of records needs dozens of disk reads = SLOW.

Solution: Store multiple keys per node (M children per node). The tree becomes very wide and very shallow. A massive database can be searched with only 3-4 disk reads!
B-Tree Rules:
  • Each node can hold multiple keys (M-way search array).
  • Every inner node (except root) is at least half full: M/2−1 ≤ keys ≤ M−1.
  • Keys & values stored in ALL nodes.
B-Tree Insertion (The Split):
  1. Overflow: A leaf node exceeds its max keys.
  2. Median Identify: Find the middle key.
  3. Split & Push: Split node at median; push center key up to parent. Tree grows UPWARD.
An improved B-Tree. All actual data lives in leaf nodes only. Inner nodes store only keys for routing.

The Sibling Pointer Advantage: Leaf nodes are linked horizontally as a linked list! Once you find the start of a range, you just scan leaves → lightning-fast range queries without going back up the tree.

Module 02 — Algorithm Complexity
Big-O Notation
Big-O measures how an algorithm's time or space grows as input size (n) increases. It's about growth rate, not exact time.
🧠 Key Insight
Big-O = Worst Case Growth. Drop constants. Keep the dominant term.
O(100n²) = O(n²) because constants don't matter at large scale. O(n² + n) = O(n²) because n² dominates. Always focus on the fastest-growing term.

⚡
O(1) — Constant
Same time regardless of input size. Example: accessing array[5], checking if a number is even. The holy grail.
📉
O(log n) — Logarithmic
Halves the problem each step. n=1,000,000 only takes ~20 steps! Binary search, BST operations on balanced trees.
📊
O(n) — Linear
One operation per element. n=1000 → 1000 ops. Linear search, scanning an array. Acceptable.
⚠️
O(n log n) — Linearithmic
The best possible for comparison-based sorting. Merge, Quick, Heap sort. Not ideal but unavoidable for sorting.
🐢
O(n²) — Quadratic
Nested loops. n=1000 → 1,000,000 ops. Bubble, Selection, Insertion sort worst case. Avoid for large data.
💀
O(2ⁿ) — Exponential
Doubles with each input. n=30 → 1 billion ops. Brute force password cracking. Almost always impractical.

ETC Formula
ETC_i = t_i / t_0    (Running time of input size i ÷ running time of the smallest base point)

This accounts for real-world crossover between algorithm theory, compilation, and hardware. Your module used the UCI Iris Dataset to empirically test sorting algorithms.
Big-O (O)
Upper bound. Worst case. The algorithm takes AT MOST this long. "It won't be slower than this."
Theta (Θ)
Tight bound. Both upper and lower. The algorithm takes EXACTLY this growth rate. "It's precisely this."
💡 Key Insight from your slides
The worst-case running time for BST operations is directly proportional to the tree height (h).
Complete binary tree → height = log n → Θ(log n)
Linear chain (degenerated) → height = n → Θ(n)

📌 Last-Minute Reminders
5 things to remember walking into the exam
1. Binary Search needs sorted data. If unsorted, sort first → total cost = O(n log n).
2. BST worst case = sorted insertion → degenerates to linked list → O(n).
3. In-order traversal of BST = sorted output.
4. Quick Sort is fastest empirically but O(n²) worst. Merge Sort guarantees O(n log n) always.
5. B+ Tree = leaves linked horizontally = fast range queries. Used in modern SQL databases.
